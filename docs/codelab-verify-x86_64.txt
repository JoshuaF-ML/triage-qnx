=== step 3: a pool thread AND an unserialised handler
  A lazy client asks for 3s of thinking at priority 10. An urgent
  client asks for 1ms at priority 40, one second later. Three
  servers, same source, two flags:

    -t 8        eight pool threads, and the lock that
                iofunc_func_init() installs for you
    -t 8 -u     eight pool threads, that lock cleared
    -t 1 -u     one thread, lock cleared

  Only the middle one can serve the urgent client. The pool and
  the missing lock are both necessary, and neither is sufficient.

  Note -W below: the urgent client opens the device BEFORE the
  server gets busy. open() is a message to the same resource
  manager and queues on the same threads, so a client that opens
  late pays the queueing inside open() -- outside the timed
  region -- and reports a latency that looks fine. That mistake
  is how this step first appeared to pass.
